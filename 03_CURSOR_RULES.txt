NEXOPS — CURSOR RULES

1. Read the project architecture and instruction files before implementing a new stage.

2. Build only the current requested stage.

3. Do not build future stages unless explicitly asked.

4. Do not create unnecessary files.

5. Do not add unnecessary dependencies.

6. Keep code simple and readable.

7. Prefer small services over one huge application.

8. Explain important implementation decisions after completing a stage.

9. Do not hide complexity behind unnecessary abstractions.

10. Do not introduce databases, Redis, Kafka, queues, service meshes, or other infrastructure unless there is a clear requirement.

11. Never hardcode passwords, API keys, tokens, AWS credentials, GitHub credentials, or other secrets.

12. Use environment variables or proper secret mechanisms for secrets.

13. Never put corporate credentials or corporate information into this project.

14. The project must remain independent from Amdocs.

15. The corporate POC environment may require a proxy.

The proxy is ONLY an environment-specific build/runtime setting.

Do NOT make the proxy part of the application architecture.

Production/AWS deployment must not depend on the Amdocs proxy.

16. Do not copy proprietary Amdocs code, documentation, configurations, credentials, or customer information into NexOps.

17. For Kubernetes permissions, use least privilege.

18. Never allow the AI service to execute arbitrary shell commands.

19. AI recommendations must pass through application validation before remediation.

20. Dangerous Kubernetes actions must never be automatically executed.

21. Use structured responses between services where appropriate.

22. Add tests for important application behavior.

23. Keep Dockerfiles simple and secure.

24. Use non-root containers where practical.

25. Add health endpoints to services.

26. Use resource requests and limits for Kubernetes workloads.

27. Do not optimize prematurely.

28. Do not rewrite working code without a reason.

29. When something fails, explain the cause and fix rather than silently changing unrelated parts.

30. After completing a stage, report:
- what was created
- files changed
- how to run it
- how to test it
- known limitations
- what should be done next

31. Do not move to the next stage automatically.

32. Keep the final project easy for a DevOps engineer with around 2 years of experience to understand and explain.
